## What is encrypted, and between whom

```
native app  ──WSS──▶  relay  ──h2 CONNECT──▶  daemon  ──loopback──▶  its own server
   │                    │                        │
   └────────── Noise_IK session ─────────────────┘
              (the relay forwards bytes it cannot read)
```

**`Noise_IK_25519_ChaChaPoly_BLAKE2s`, and it is the only mode.** The app opens a
WebSocket to the relay at `/__relay/channel`; the relay authorizes it exactly as it
authorized a request before — verify the JWS, take `machineId` from `aud`, read the
live user / machine / grant rows — and splices it to one h2 `CONNECT` stamped
`reemoat-enc: noise-ik-25519-chachapoly-blake2s/1`. It parses nothing after that.
Q7.37, Q7.143.

**Two static keys, and neither is shared.** The initiator's is the **device key**:
one X25519 keypair per installation per **account** — a server and a user on it —
generated by the native shell, kept in the OS keyring (`device_key#<origin>#<user
id>`) with a `0600`-file fallback, and used *from Rust* — `host_device_dh` answers a
shared secret with the calling webview's account's key and the page never holds it.
Per account because `devices.public_key` is not unique: one key on two users' rows
tells anybody who can see both that they are one computer, and one account's Re-key
would strand the other's binding. The one key that ever moves is a pre-accounts key
under the bare origin, and only to the account proved to own it. Q1.651. The responder's is the
**machine key**: generated by the daemon on first start into `machine_keys`,
announced on every tunnel dial beside `DAEMON_VERSION_HEADER`, and reported to the
app by `POST /v1/tokens` beside `relayUrl`. There is no fleet-wide or user-wide
symmetric key anywhere, and no user private key: two devices of one person derive
independent session keys and share nothing.

⚠ **That `0600` is a statement about `config.rs`'s code and it was a statement
about nothing for four releases.** Two docblocks and this file said `0600` while
`write_stored` used `fs::write`, which creates at `0666 & !umask` — `0644` under the
usual one — and, on a file that already exists, opens the old inode and keeps
whatever mode it already had. The fallback's whole population is machines with no
usable keyring, which is a shared host with somebody else on it. It is enforced at
creation now, by `OpenOptions::mode(0o600)` on a temporary file plus a rename over
the target: the mode at creation closes the window in which the bytes sit at the
umask's, and the **rename** is what narrows installations that already exist, which
a mode set only at creation would have left world-readable for ever while looking
green in a test that started from an empty directory. `set_permissions` runs on the
open handle as well, because `mode()` is masked and a umask with owner bits in it
would leave a key file this same user cannot read back — which is the
regenerate-on-every-launch failure the fallback exists to prevent. `cargo test` in
`config.rs` asserts the mode, the upgrade path, the `0700` on the directory and
the temporary a failed rename has to take with it — and one of those re-executes
the test binary under `umask 0277`, because at the usual `022` **both** halves of
the mode answer `0600` on their own and deleting either one left every other
assertion in that file green. `nativecheck` greps the same lines out of
`write_stored` from the `check` job, which runs no cargo at all.

**IK because the app already knows the machine's key**, which is IK's precondition
and what lets the app establish it reached the **expected machine** rather than
trusting the relay's routing. One round trip rather than XX's two.

## Invariants

- **The capability rides the first *transport* message, never the handshake
  payload.** Message 1 is encrypted to a static key alone — no forward secrecy, and
  replayable verbatim — so a capability in it would be replayable off the wire for
  its whole lifetime. ⚠ **Not enforced in `noise.ts`, deliberately**: that file
  implements the specification, which allows a payload in every message, and the
  published vectors carry one in all four. The rule belongs to the layer that
  decides what to send. Q5.118.
- **Reaching `split()` *is* the machine's authentication.** Message 2 is sealed
  under a key mixed from `ee` and `se`, so only the holder of the private half of
  the static the initiator started with can produce one. There is no name to check
  and no comparison to read — the absence of one is the property, not an omission.
- **A tag failure ends the session and sends nothing.** No resynchronise: a
  diverged nonce fails every later frame, so "skip it and carry on" is a session
  that never works again while appearing to try. Below a failed handshake there is
  no key to send a refusal under, which is the one refusal in this codebase that
  cannot say why.
- **`RESPONSE_END` and `FAILED` are different frames**, and `fail()` must `end()`
  the stream rather than `destroy()` it — a destroyed stream drops the frame it
  just wrote, which turns a `502 truncated` back into a transport failure the
  client retries for ever. Q6.103, Q5.118.
- **The session pins its own capability onto every inner request** and replaces any
  the client sent. Binding only at the handshake would mean one capability opening
  the session and another doing the work. It also retires `?token=` on the last
  hop: Node makes that request and can set a header.
- **`RelayTunnel.open` takes `encryption` with no default.** There is no spelling
  of that call that produces an unencrypted stream. It used to write `"none"`
  itself, which made the carrier the party that chose.
- **No second timer against Q5.24.** The pool's reuse margin decides only whether
  an *idle* connection is handed out again; nothing tears a live one down on a
  clock. The daemon's own expiry re-check is still what ends a session.

## The device binding

**Authentication, not authorization.** A grant is still `(user_id, machine_id)` and
still full access; `relay/authorize.ts` reads no device row and must not learn to.
The capability names the device's key in RFC 7800 `cnf.jkt`; the handshake proves
possession; the daemon compares them **offline**, which is what keeps *"the daemon
makes exactly one control-plane request, ever"* literally true. Q1.648.

⚠ **A capability with no `cnf` is refused on a channel** (`unbound_capability`)
rather than treated as unbound — without that the binding is optional, and a caller
gets bearer semantics by not asking for a binding. `parseClaims` returns `null` for
a `cnf` that is present but malformed, which is the same rule one layer down.

⚠ **`wrong_device` is recoverable and the client recovers it.** A credential store
reset out from under the app leaves the shell holding a key the Authority has never
been told about — and minting still *succeeds*, because the Authority has a key on
file and nothing to compare it against. The daemon is the first party that can see
the disagreement. `MachineChannel` re-registers the same device id **once** (which
writes the key in place, spending no device slot) and retries. Once, for `mint`'s
reason: a re-registration that does not take must surface as the refusal it is
rather than as a loop against the Authority.

## Connections

**A pool, not a multiplexer.** One connection carries one thing at a time, the way
HTTP/1.1 keep-alive does. Collapsing a machine's traffic onto one encrypted session
would put every request behind one h2 window — a paused download would stall the
live event socket — and the only fix is per-stream credit accounting, which is
reimplementing the half of HTTP/2 already underneath. A live event stream takes a
connection of its own and keeps it. Q4.122's sibling argument is in
`packages/protocol/src/frames.ts`.

**The daemon parses; the browser does not.** The relay's own docblock made this
argument about itself: `http.request({createConnection})` lets Node serialize a
request, decide chunked-versus-content-length and raise `upgrade` for a 101.
Splicing raw bytes to loopback would move exactly that hand-writing into the
**webview** — an HTTP/1.1 response reader and an RFC 6455 client, where desync bugs
with security consequences live. Moving the parse from the relay to the daemon
keeps Node doing it. ⚠ This does **not** weaken *"the tunnel carries opaque bytes,
not parsed HTTP"* (Q1.25): that is a property of the tunnel and of the relay, and
the relay in fact gains it. The daemon is one **endpoint** of the session and is
supposed to understand what it terminates.

## What is not defended against

**A malicious Authority.** It mints every capability and holds
`signing_keys.private_pem`, so it can issue one naming a device key of its own and
reach your daemon as you. E2EE removes the **relay** from the trusted payload path;
it does not make the operator untrusted, and they still ship the client.

**A capability spent over loopback.** There is no channel there, so there is no key
to compare, so on that one path a capability is a bearer token for its remaining
life. `.claude/rules/relay.md` already bounds that trade and `SECURITY.md` states
it in the revocation table.

**Anything on the machine itself.** The daemon runs agents as you, unconfined. The
encryption is about the wire.

## Layout

| File | Holds |
|---|---|
| `packages/protocol/src/noise.ts` | The handshake, written to the specification. `dh` is async **because the app's static lives in Rust** — that seam is what lets one implementation serve both ends |
| `packages/protocol/src/frames.ts` | What travels inside: the frame table, the length prefixing, `LengthReader` |
| `packages/protocol/vectors/noise.txt` | The published vector. ⚠ `.txt` rather than `.json`, because `docscheck`'s `SOURCE_EXT` includes `json` and would pull it into the corpus every cited symbol is grepped against |
| `src/e2ee.ts` | The daemon's responder: terminate, check the capability against the authenticated key, serve loopback with Node's own clients |
| `packages/web/src/e2ee.ts` | The app's initiator, the pool, and the `WebSocket`-shaped adapter `stream.ts` consumes |
| `src/machinekey.ts` | The daemon's own static, generated once into `machine_keys` |
| `packages/control-plane/src/machinekeys.ts` | Trust-on-first-use pinning, and the 409 on a disagreement |
| `packages/native/src-tauri/src/device.rs` | The device key, and the DH that never returns it |

## Verification

`pnpm protocolcheck` drives the handshake byte-for-byte against the published
cross-implementation vectors **in both roles** — fixed ephemerals, so "we
implemented Noise" is an assertion rather than a claim. `scripts/daemoncheck.e2ee.ts`
drives the real `serveSecureSession` against the real `createApp` with a
hand-written client, so it can send bytes an honest client never would.
`packages/web/scripts/webcheck.e2ee.ts` is the mirror and the more important of the
two: the **real** `MachineChannel` against the **real** `serveSecureSession`, with
every byte the relay carried recorded and asserted unreadable.

⚠ **The two copies of `RELAY_CHANNEL_PATH` are compared by a check, not by an
import, and by exactly *one* check.** The relay may reach the repository root for
exactly five files and carries no `@reemoat/protocol` in its image; `packages/web`
may import neither `src/` nor the control plane. So it is two literals, and
`packages/web/scripts/webcheck.e2ee.ts` is the only thing in the tree that compares
them: it reads `listener.ts` off disk, pulls the declared literal out with a regular
expression, and matches it against the one it imported. A client dialling a path the
relay does not serve is a fleet where no machine is reachable, and that assertion is
the whole of what stands between here and there.

⚠ **Three docblocks say `relaycheck` compares them and it does not.** It imports
`RELAY_CHANNEL_PATH` from `listener.ts` and never opens `packages/web/src/e2ee.ts`
at all, so every path it dials is the relay's own constant agreeing with itself —
green whatever the app is spelling. The claim is written in
`packages/control-plane/src/relay/listener.ts`, in `packages/web/src/e2ee.ts`, and,
worst of the three, inside `webcheck.e2ee.ts`'s own comment as *"`relaycheck` holds
the same assertion from the other side"*. That last one is the dangerous shape
rather than merely the wrong one: a belief in a second copy is what makes the first
look like redundancy, and redundancy is what gets deleted. **Two defences under one
assertion is either redundancy or two properties sharing a name, and only knocking
them out one at a time says which** — here there was never a second defence to
knock out.
