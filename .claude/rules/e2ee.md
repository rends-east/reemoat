## What is encrypted, and between whom

```
native app  ──WSS──▶  relay  ──h2 CONNECT──▶  daemon  ──loopback──▶  its own server
   └────────── Noise_IK session ─────────────────┘   (the relay forwards bytes it cannot read)
```

**`Noise_IK_25519_ChaChaPoly_BLAKE2s` is the only mode.** The relay authorizes the app's
WebSocket at `/__relay/channel` (the JWS, `machineId` from `aud`, the live user / machine /
grant rows), splices it to one h2 `CONNECT` stamped
`reemoat-enc: noise-ik-25519-chachapoly-blake2s/1`, and parses nothing after. IK because the
app already knows the machine's key, so it proves it reached the **expected machine**, in one
round trip. Q7.37, Q7.143.

**Two static keys, neither shared.**

- **Device key** (initiator): X25519, one per installation per **account**, generated by the
  shell, in the OS keyring (`device_key#<origin>#<user id>`) with a `0600`-file fallback, used
  *from Rust*: `host_device_dh` answers a shared secret for the calling webview's account; the
  page never holds the key. Per account because `devices.public_key` is not unique: one key on
  two users' rows links them. Only a pre-accounts bare-origin key moves, to the account proved
  to own it. Q1.651.
- **Machine key** (responder): generated by the daemon on first start into `machine_keys`,
  announced on every dial beside `DAEMON_VERSION_HEADER`, reported by `POST /v1/tokens` beside
  `relayUrl`.

No fleet-wide or user-wide symmetric key, no user private key.

**The fallback is `0600` at creation**: `write_stored` (`config.rs`) writes a temporary with
`OpenOptions::mode(0o600)`, renames it over the target (narrowing existing files), and calls
`set_permissions` on the handle since `mode()` is umask-masked. Its `cargo test` asserts mode,
upgrade, the `0700` directory and temp cleanup, one under `umask 0277`; `nativecheck` greps
the same lines without cargo.

## Invariants

- **The capability rides the first *transport* message, never the handshake payload**:
  message 1 has no forward secrecy and replays verbatim. Not enforced in `noise.ts`, which
  follows the specification; the sending layer owns it. Q5.118.
- **Reaching `split()` *is* the machine's authentication** (message 2 is sealed under `ee` and
  `se`); there is no name to check.
- **A tag failure ends the session and sends nothing**; no resynchronise. A failed handshake
  has no key to refuse under, the one refusal here that cannot say why.
- **`RESPONSE_END` and `FAILED` are different frames**, and `fail()` must `end()` the stream,
  never `destroy()` it, which drops the frame just written and turns a `502 truncated` into a
  transport failure retried for ever. Q6.103, Q5.118.
- **The session pins its own capability onto every inner request**, replacing the client's
  (and retiring `?token=` on the last hop).
- **`RelayTunnel.open` takes `encryption` with no default.**
- **No second timer against Q5.24**: the pool's reuse margin applies to *idle* connections
  only; the daemon's expiry re-check ends a session.

## The device binding

**Authentication, not authorization.** A grant is still `(user_id, machine_id)` and full
access; `relay/authorize.ts` reads no device row and must not learn to. The capability names
the device key in RFC 7800 `cnf.jkt`, the handshake proves possession, and the daemon compares
them **offline**, so it still makes exactly one control-plane request, ever. Q1.648.

- **A capability with no `cnf` is refused on a channel** (`unbound_capability`), or a caller
  gets bearer semantics by not asking for a binding. `parseClaims` returns `null` for a present
  but malformed `cnf`.
- **`wrong_device` is recoverable**: a reset credential store leaves a key the Authority never
  saw, and minting still succeeds. `MachineChannel` re-registers the same device id **once**
  (the key written in place, no new slot) and retries, once, so a failure surfaces, not loops.

## The machine's own list of devices

**`known_devices` is the daemon's, and the Authority neither reads nor writes it.**
`DeviceGate.admit` runs once per channel, **after** the capability verified (an unsigned
stranger must not write a row). Unlocked it is a journal and lets everybody in; locked it
is the allowlist, and a key not `known` is refused `DEVICE_NOT_APPROVED` and filed
`pending`. Off until somebody turns it on. Q1.655.

- **`DEVICE_NOT_APPROVED` is not `wrong_device`**: that one re-registers the key and
  retries, which cures nothing here. The app reads it as `device_pending`, and the
  sending daemon of a link says so in words.
- **The device names itself in the hello** (`HelloFrame.device`, optional both ways):
  inside the channel, so it is not the Authority's claim. Drawn, never decided on.
- **Turning the lock on grandfathers the list**, and takes the caller's own key with it
  (`vouch`, checked against `cnf.jkt`): a device that only ever used loopback has no row.
- **Loopback is outside the list** (no channel, no key): `pnpm client devices` on the
  machine is the way back in after every device is lost. The listener holds it to this
  computer first: a foreign `Origin` or, bound to loopback, a foreign `Host` is a 403
  before CORS (`src/origin.ts`), and a daemon bound beyond loopback refuses the lock.
- **A removed key's open channels end at once** (`watch`), and `DELETE` refuses the key
  the request rides on (`409 own_device`), which would end the channel carrying the answer.
- **A locked list is never trimmed**; the journal and the pending rows are bounded.
- **The code is `approvalCode(asking key)`, ten characters, and of that one key**: with
  the machine's key in it too, one party chose a key on each side and equal codes cost
  2^25. Which machine was reached is `keyFingerprint`'s. One implementation, in
  `packages/protocol`, with a pinned vector. Q1.656.
- **A claimed name may not carry a code**: `drawable` removes what nobody sees and any
  token that `readsAsCode`, for a name, a link's label and a platform; the screen draws
  the code on a line holding nothing the device chose. Q1.656.

## The key a machine was first reached with

**The app believes `POST /v1/tokens` about a machine's key once** (`storedPins`, per
server, `localStorage`). `weighOfferedKey` is total over held × named: a different key
later is **never dialled**; the held one is, and only if it no longer answers does the
machine read `machine_key_changed`, cleared by a person (`acceptOfferedKey`, which takes
the fingerprint that was compared and refuses another). Never raised while the link
itself is in doubt (`linkInDoubt`). So a lie about the key costs the reader nothing. A
key read over loopback is the machine's own word and re-pins silently (`learnLocalKey`,
`GET /health`'s `machineKey`). A miss re-reads storage and a write merges: every
account's webview shares the one value. Q1.657.

**Alone it is worth little**: it covers a compromise *after* first contact, against
being read, never against being entered. First contact is closed by the lock's code or
by comparing `keyFingerprint` by eye with what the daemon prints at start.

## Connections

**A pool, not a multiplexer**: one connection, one thing at a time, or a paused download stalls
the live event socket behind one h2 window. A live event stream keeps its own connection
(Q4.122's sibling argument is in `packages/protocol/src/frames.ts`); **a download piece takes
its own and closes it** (`alone`), needing a whole window (Q6.120).

**The daemon parses; the browser does not.** `src/e2ee.ts` serves loopback through
`http.request({createConnection})`, keeping HTTP/1.1 and RFC 6455 parsing in Node, out of the
webview. The tunnel and relay still carry opaque bytes (Q1.25); the daemon is an endpoint.

## What is not defended against

- **A malicious Authority, on an unlocked machine**: it mints every capability and holds
  `signing_keys.private_pem`, so it can name a device key of its own. E2EE removes the
  **relay** from the trusted path; the lock removes the Authority's signature as a way in,
  for whoever turns it on. The operator still ships the client and still routes.
- **A capability spent over loopback**: no channel, so no key to compare; a bearer token for its
  remaining life (`relay.md`; `SECURITY.md`'s revocation table).
- **Anything on the machine itself**: agents run as you, unconfined.

## Verification

`pnpm protocolcheck`: the published vectors **in both roles**, fixed ephemerals.
`scripts/daemoncheck.e2ee.ts`: the real `serveSecureSession` and `createApp` against a
hand-written client. `packages/web/scripts/webcheck.e2ee.ts`, the more important: the **real**
`MachineChannel` against the **real** `serveSecureSession`, every relayed byte asserted unreadable.

`scripts/daemoncheck.devices.ts`: the store, the gate, the real responder and the routes.
`webcheck.device-trust.ts`: every pair of held and named key, a connection through a
change and through a wait, and the two spellings of `DEVICE_NOT_APPROVED` compared.

**The two copies of `RELAY_CHANNEL_PATH` are compared by exactly one check**: the relay carries no
`@reemoat/protocol` and `packages/web` may import neither `src/` nor the control plane, so
`webcheck.e2ee.ts` reads `listener.ts` off disk and matches its literal against the imported one.
**`relaycheck` does not compare them**, whatever the docblocks in
`packages/control-plane/src/relay/listener.ts`, `packages/web/src/e2ee.ts` and `webcheck.e2ee.ts`
say: it only ever dials the relay's own constant. Do not delete the one real check as redundancy.
